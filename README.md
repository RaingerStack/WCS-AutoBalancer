# WarcraftAutoBalance v2.12 — Full Implementation Guide

## 1. Purpose

WarcraftAutoBalance is a CounterStrikeSharp plugin for a Warcraft-style CS2
server. It balances human team strength while accounting for player performance,
persistent skill, Warcraft race strength, race level, low-population conditions,
disconnects, bots, and the unusual combat behavior created by Warcraft races.

v2.11 uses SQLite exclusively for persistent data. Active gameplay calculations
remain in RAM.

---

## 2. Architecture

```text
CounterStrike 2 / CounterStrikeSharp
        |
        +-- Warcraft mod
        |     +-- selected base race
        |     +-- race level
        |     +-- abilities / summons / respawns
        |
        +-- WarcraftAutoBalance
              +-- current-round state ........ RAM
              +-- active player ratings ...... RAM
              +-- race performance cache ..... RAM
              +-- persistent player history .. SQLite
              +-- recent 12 real rounds ...... SQLite
```

The design rule is:

```text
high-frequency gameplay = RAM
durable historical state = SQLite
```

No database operation belongs in damage, kill, assist, or other high-frequency
combat handlers.

---

## 3. Requirements

- Counter-Strike 2 dedicated server
- Metamod
- CounterStrikeSharp
- .NET 8 compatible plugin project
- `Microsoft.Data.Sqlite`
- Warcraft mod integration capable of reporting each player's selected base race
  and current/max race level

The server should disable CS2's native team balancing:

```cfg
mp_autoteambalance 0
mp_limitteams 0
```

WarcraftAutoBalance must be the system responsible for intentional team
composition changes.

## 5. Persistent Database

The database file is:

```text
balance.db
```

SQLite may also create while running:

```text
balance.db-wal
balance.db-shm
```

These are normal WAL files.

Connection configuration:

```sql
PRAGMA journal_mode = WAL;
PRAGMA synchronous = NORMAL;
PRAGMA foreign_keys = ON;
PRAGMA busy_timeout = 5000;
```

WAL provides efficient local writes and allows future reporting/admin readers to
coexist more cleanly with the game server.

## 6. Database Tables

### Metadata

Stores small plugin-wide values such as schema version and completed round
number.

```sql
CREATE TABLE Metadata (
    Key TEXT PRIMARY KEY,
    Value TEXT NOT NULL
);
```

### Players

```sql
CREATE TABLE Players (
    SteamId INTEGER PRIMARY KEY,
    Name TEXT NOT NULL,
    HistoricalRating REAL NOT NULL DEFAULT 1000,
    LifetimeRounds INTEGER NOT NULL DEFAULT 0,
    LifetimeWins INTEGER NOT NULL DEFAULT 0,
    CreatedUtc TEXT NOT NULL,
    LastSeenUtc TEXT NOT NULL
);
```

SteamID64 is the permanent player identity.

### RecentRounds

```sql
CREATE TABLE RecentRounds (
    SteamId INTEGER NOT NULL,
    RoundId INTEGER NOT NULL,
    PlayedUtc TEXT NOT NULL,
    Damage INTEGER NOT NULL,
    Kills INTEGER NOT NULL,
    Deaths INTEGER NOT NULL,
    Assists INTEGER NOT NULL,
    Survived INTEGER NOT NULL,
    Contributed INTEGER NOT NULL,
    TeamWon INTEGER NOT NULL,
    ObjectivePoints REAL NOT NULL,
    PRIMARY KEY (SteamId, RoundId),
    FOREIGN KEY (SteamId)
        REFERENCES Players(SteamId)
        ON DELETE CASCADE
);
```

Lookup index:

```sql
CREATE INDEX IX_RecentRounds_SteamId_RoundId
ON RecentRounds (SteamId, RoundId DESC);
```

### RaceStats

```sql
CREATE TABLE RaceStats (
    RaceName TEXT PRIMARY KEY COLLATE NOCASE,
    RoundsPlayed INTEGER NOT NULL DEFAULT 0,
    ActualWins REAL NOT NULL DEFAULT 0,
    ExpectedWins REAL NOT NULL DEFAULT 0,
    LastCalculatedModifier REAL NOT NULL DEFAULT 1.0
);
```

## 7. Player Memory Model

Historical population does not equal RAM population.

At startup, the plugin does not load every historical player.

```text
player becomes relevant
→ indexed lookup by SteamID64
→ load player record
→ load at most latest 12 real rounds
→ keep active PlayerBalanceData in RAM
```

On disconnect:

```text
persist player
→ commit
→ remove player from active RAM dictionaries
```

Therefore a database containing tens or hundreds of thousands of historical
players does not require all of those player objects to remain resident.

Race statistics remain globally cached because the number of races is tiny.

---

## 8. Rolling Recent-Round Window

`RollingWindowRounds = 12`.

Only real completed rounds are represented.

A player with four tracked rounds has four snapshots. The remaining eight slots
do not exist and contribute nothing.

Cross-session example:

```text
Day 1: play 4 rounds → 4 stored
Day 2: reconnect → load 4
       play 4       → 8 stored
Day 3: reconnect → load 8
       play 4       → 12 stored
next real round     → oldest drops, newest 12 remain
```

Reconnect query:

```sql
SELECT ...
FROM RecentRounds
WHERE SteamId = $steamId
ORDER BY RoundId DESC
LIMIT 12;
```

The returned rows are reversed into chronological order in RAM.

---

## 9. Efficient Round Persistence

Every newly completed snapshot receives:

```text
RoundId
PlayedUtc
PendingPersistence
```

`PendingPersistence` exists only in runtime memory.

A normal completed round creates one new RecentRounds insert for each active
human:

```sql
INSERT INTO RecentRounds (...)
VALUES (...)
ON CONFLICT(SteamId, RoundId) DO NOTHING;
```

Already persisted snapshots are not rewritten.

After the transaction succeeds, pending flags are cleared. If the transaction
fails, the flags remain pending so the data can be retried.

An indexed prune keeps each player physically bounded to the newest 12 rows.

This gives strong durability without putting storage operations in combat-event
hot paths.

## 10. Round Statistics

Tracked direct human combat data includes:

- damage
- kills
- deaths
- assists
- survival
- approximate KAST/contribution
- bomb plant contribution
- bomb defuse contribution
- round win/loss

Bots do not contribute to human rating statistics.

Damage/kills caused by independent summon or projectile entities should not be
guessed as belonging to a human owner. The preferred future integration is an
explicit owner-attribution API from the Warcraft mod.

---

## 11. Respawn-Safe Survival

Warcraft races may respawn players during the same round.

Survival is therefore:

```csharp
bool survived = !round.Died;
```

It is not determined from pawn health at round end.

If a player dies and later respawns:

```text
Died = true
Survived = false
```

This prevents resurrection mechanics from generating false survival credit.

Multiple actual deaths may count as multiple deaths. Deaths are not artificially
capped at one because doing so while retaining additional post-respawn kills
would inflate resurrection races.

---

## 12. Approximate KAST / Contribution

A player contributes when they achieve at least one of the plugin's tracked
impact conditions, including kills, assists, survival, or meaningful damage.

The current implementation uses an approximate KAST-style metric rather than
full trade-kill reconstruction.

This is intentional: it captures useful round participation cheaply.

---

## 13. Recent Player Rating

Weights:

```text
ADR ............... 35%
K/D ............... 25%
Historical rating . 20%
KAST .............. 10%
Objective impact .. 10%
```

### Warcraft-scale ADR and K/D

Warcraft gameplay can legitimately create several hundred ADR and K/D values
well above conventional Counter-Strike ranges.

ADR and K/D therefore use an inexpensive logarithmic diminishing-return
transform instead of a simple linear scale with a low ceiling.

Reference points:

```text
ADR reference .... 100
K/D reference .... 1.0
```

At the reference point the component rating is 1000. Above the reference,
component rating continues to rise but with diminishing returns.

Approximate raw transform behavior:

```text
ADR       component rating
  50      ~743
 100      1000
 200      ~1347
 400      ~1693
 800      ~2040
1200      ~2242

K/D       component rating
 0.5      ~774
 1.0      1000
 2.0      ~1291
 5.0      ~1676
10.0      ~1967
25.0      ~2352
50.0      ~2600 safety ceiling
```

This means 5, 15, and 25 K/D remain meaningfully different while a single
extreme stat cannot scale linearly without limit and dominate the complete
balance score.

### Small-sample K/D smoothing

K/D is calculated from aggregate kills and deaths in the real recent-round
window with a small Bayesian-style prior:

```text
effective K/D = (kills + 3) / (deaths + 3)
```

Examples:

```text
10-0   -> 4.33 effective K/D
25-0   -> 9.33 effective K/D
100-4  -> 14.71 effective K/D
250-10 -> 19.46 effective K/D
```

A brand-new flawless streak therefore receives strong credit without being
treated identically to sustained elite performance over a much larger sample.
As real engagements accumulate, the 3/3 prior becomes increasingly insignificant.

### Safety bounds and performance cost

ADR and K/D component ratings have only a wide emergency range:

```text
450 .. 2600
```

The logarithmic transform provides normal differentiation; the bounds are
primarily protection against pathological values.

The implementation adds only a `Math.Log` and a few arithmetic operations per
ADR/KD component when a player rating is evaluated. It adds no database work and
no computation to damage, death, assist, objective, or other high-frequency
combat events.

The exact same normalization is used by both the current player rating and the
historical-rating learning calculation, so the two systems cannot drift apart.

Players with fewer than 12 rounds use only the real rounds available. Missing
rounds never exist and never contribute zeros.

---

## 14. Historical Rating

New players begin around:

```text
1000
```

Historical rating moves gradually toward observed recent performance using a
small EMA-style learning rate.

Current design:

```text
HistoricalLearningRate = 0.05
```

Historical rating is intentionally slower than the rolling recent window. This
provides stability when a player has a temporary hot or cold streak.

---

## 15. Warcraft Race Assignment

The Warcraft mod should report the selected persistent/base race:

```csharp
SetPlayerRace(
    player,
    raceName,
    currentLevel,
    maximumLevel);
```

Call this when:

- a player selects a base race;
- the selected base race changes;
- the base race level changes.

Do not call it merely because an ability temporarily respawns the player as a
summon or alternate form.

The original base race should receive the round-result influence caused by its
own resurrection/transformation mechanics.

---

## 16. Race Level Modifier

Race level provides a deliberately small adjustment around neutral.

Approximate range:

```text
low level .... ~0.98
mid level ....  1.00
max level .... ~1.02
```

The level adjustment is intentionally much smaller than the player-skill model.

---

## 17. Learned Race Strength

Race power is learned automatically.

The plugin does not simply say:

```text
race won 57% → race is +7% strong
```

Instead it compares actual race results with the expected results of the players
and teams using that race.

Example:

```text
actual race win rate .... 57.0%
expected win rate ....... 54.4%
race performance edge ... +2.6%
```

This reduces the chance that strong players selecting a race make the race itself
look overpowered.

Current concepts:

```text
minimum sample rounds ..... 40
prior/shrinkage rounds .... 100
sensitivity ............... 0.75
modifier clamp ............ 0.95–1.05
```

Bayesian-style confidence shrinkage keeps low-sample races close to neutral.

---

## 18. Final Player Balance Value

Conceptually:

```text
base player rating
× learned race modifier
× race level modifier
=
final balance rating
```

This separates player skill from current Warcraft combat power.

---

## 19. Pre-Round Expected Win Chance

Race learning uses a frozen pre-round expectation.

At round start, the plugin snapshots:

- real human participants;
- their starting team;
- player skill without current race outcome contamination;
- human team counts.

That expectation remains frozen for the round.

Disconnects, deaths, respawns, temporary forms, or pawn changes later in the
round do not retroactively alter what the expected outcome was before combat.

---

## 20. Human Count Adjustment

An extra real human matters.

The expectation model therefore includes a modest player-count adjustment:

```text
PlayerCountExpectationAdjustment = 75 rating points
```

This is intentionally not enormous because Warcraft abilities can create extra
lives, summons, and other combat power not represented by simple body count.

Those mechanics are instead learned through race performance.

---

## 21. Expected Win Formula

Team rating differences are converted into expected probability using an
Elo-style function:

```text
1 / (1 + 10^((opponentRating - teamRating) / 400))
```

This provides an interpretable measure such as:

```text
50/50
55/45
58/42
65/35
```

rather than balancing on raw rating difference alone.

---

## 22. Initial Balance Before Round 1

The plugin does not switch already-alive warmup players and then manually
respawn/teleport them.

Instead:

```text
warmup
→ players choose races
→ warmup ends
→ first non-warmup round_prestart
→ read CURRENT humans and race assignments
→ calculate starting partition
→ SwitchTeam()
→ CS2 continues normal round restart/spawn
→ Round 1 begins
```

The initial pass does not call:

```text
Respawn()
slay/kill
manual spawn teleport
pawn replacement
```

This avoids triggering Warcraft resurrection, spawn, cooldown, death, or summon
logic.

---

## 23. Initial Balance: 2–6 Humans

For low population, the nonlinear adaptive partition is used immediately.

Possible human splits include:

```text
1v1
1v2
1v3
1v4
1v5
2v2
2v3
2v4
3v3
```

The goal is effective human power, not equal human count.

---

## 24. Low-Population Effective Power

Low-pop balance uses nonlinear power:

```csharp
Math.Exp(
    (finalRating - 1000) /
    300.0);
```

Examples:

```text
1000 rating → 1.00 power
1300 rating → 2.72 power
1600 rating → 7.39 power
```

This allows a legitimately exceptional player/race combination to be matched
against multiple weaker humans.

For 2–6 humans, every valid non-empty partition can be evaluated cheaply.

---

## 25. Initial Balance: 7+ Humans

The initial match setup is allowed to rebuild the human teams because warmup
composition is disposable.

Unlike normal mid-match balancing, it does not require a 58/42 imbalance before
acting.

The objective is the closest available starting matchup to 50/50.

For normal server populations up to 32 humans, the plugin uses an exact
meet-in-the-middle fixed-size subset search.

For unusually larger populations, it falls back to greedy selection plus local
pair-swap refinement.

Odd human counts evaluate both possible team-size orientations.

Balance quality is primary; fewer player moves is only a tie-breaker.

---

## 26. Warmup Safety

`round_prestart` can occur during warmup.

The plugin checks the game rules warmup state and also observes warmup end.

If the game rules state cannot be safely determined before warmup end is known,
the plugin delays the initial pass rather than risking an incorrect warmup
switch.

A hot reload during an already-live match must not trigger a surprise fresh
Round-1 reshuffle.

---

## 27. Normal Every-Four-Round Balance

Normal live-match balancing occurs every:

```text
4 completed rounds
```

This is intentionally different from the initial balance.

Normal balancing tries to minimize disruption.

It:

1. gets active non-bot humans;
2. handles population imbalance when needed;
3. computes average T and CT strength;
4. calculates expected win chance;
5. acts only when the stronger side reaches approximately 58%;
6. evaluates all possible single human T↔CT swaps;
7. selects the swap producing the closest result to 50/50;
8. prefers an outcome at or inside roughly 55/45;
9. moves nobody if no swap improves the current state.

---

## 28. No Swap Protection

There is intentionally no multi-round move immunity.

Maps are short and Warcraft conditions change quickly through:

- race changes;
- level changes;
- joins;
- disconnects;
- changing player performance.

Every player is therefore eligible at every balance pass.

---

## 29. Immediate Disconnect Handling

Disconnects can create urgent physical imbalance before the normal four-round
schedule.

Disconnect events are coalesced with a short delay so multiple near-simultaneous
leaves become one evaluation.

Example:

```text
10v10
→ player leaves
→ another leaves immediately
→ one delayed evaluation sees 10v8
```

A physical team-count difference of two or more triggers emergency correction.

After population correction, normal strength evaluation is run again.

---

## 30. Emergency Move Selection

When a human must move to repair population, the plugin does not simply move the
lowest scorer.

Each candidate is simulated using the rating model.

The preferred candidate:

1. repairs the count imbalance;
2. produces an expected result inside approximately 55/45 when possible;
3. otherwise produces the closest result to 50/50.

Logical team lists are updated before engine team-state propagation is trusted,
preventing the same controller from being selected twice during a multi-move
correction.

---

## 31. Bots

Bots never affect:

- player historical rating;
- ADR;
- K/D;
- KAST;
- race learning;
- objective rating.

Humans are partitioned first.

Bots are filler.

After the desired human composition is known, bot allocation is chosen to make
the physical T/CT population as even as possible while minimizing bot moves.

Logical human counts are passed into bot redistribution so delayed engine
`SwitchTeam()` state cannot corrupt the calculation.

---

## 32. SwitchTeam

Automated team changes use:

```csharp
player.SwitchTeam(desiredTeam);
```

Balancing decisions and engine movement are separate concerns:

```text
rating algorithm → decides who belongs where
SwitchTeam()     → performs the controller team change
```

Round-1 changes occur during the safe prestart transition.

Live-match changes should remain between-round operations.

---

## 33. Warcraft-Owned Entity Cleanup

The main Warcraft mod should eventually expose a callback such as:

```csharp
OnAutoBalanceTeamChanged(
    player,
    oldTeam,
    newTeam);
```

That callback should reconcile team-owned:

- summons;
- clones;
- traps;
- portals;
- projectiles;
- auras;
- other persistent Warcraft entities.

The balancer should not independently guess how every race stores its entities.

---

## 34. Custom Damage Attribution

Direct player-vs-player combat is naturally trackable.

If a projectile or summon is a separate non-human entity, the engine event may
not identify the owning human in a way the balancer can safely infer.

The preferred integration is explicit:

```csharp
ReportAttributedDamage(
    ulong ownerSteamId,
    int damage);

ReportAttributedKill(
    ulong ownerSteamId,
    ulong victimSteamId);
```

The Warcraft mod should call these only when the normal game event did not
already attribute the action to that player, preventing double counting.

---

## 35. Database Write Cadence

Persistence and balancing cadence are separate.

```text
completed round
→ one SQLite transaction

every fourth completed round
→ run normal team-balance evaluation
```

Per-round persistence limits hard-crash exposure to the unfinished current round
without putting storage work inside combat handlers.

Disconnect also flushes the departing player before eviction.

---

## 36. Resource Characteristics

High-frequency operations:

```text
dictionary lookup
integer/double increment
small in-memory state updates
```

Low-frequency operations:

```text
one transaction per completed round
one indexed player load on reconnect
team optimization every four rounds
one initial partition at match start
```

There are no continuous high-frequency polling timers for balance calculations.

The initial meet-in-the-middle search runs once and is insignificant compared
with normal CS2/Warcraft server workload at typical player counts.

---

## 37. Database Growth

Recent round storage is physically bounded to:

```text
12 rows × historical players
```

Approximate maximum RecentRounds row counts:

```text
2,000 players ....... 24,000
20,000 players ...... 240,000
100,000 players ..... 1,200,000
```

With indexed SteamID/RoundId access, this is routine SQLite scale.

The Players table itself is one row per historical SteamID64.

---

## 38. Backup Considerations

Because WAL is enabled, a running server can have:

```text
balance.db
balance.db-wal
balance.db-shm
```

Do not assume copying only `balance.db` while the server is actively writing is
a complete current backup.

Prefer either:

- backup while the plugin/database is cleanly closed; or
- an SQLite-aware backup/checkpoint process.

## 42. Production Test Plan

Before public deployment, test at minimum:

### Database
- fresh server creates `balance.db`;
- schema initializes correctly;
- WAL is enabled;
- reconnecting player loads persistent rating;
- fewer than 12 rounds remain fewer than 12;
- 12 rounds persist across multiple sessions;
- 13th round removes only the oldest;
- restart preserves player/race state;
- failed write does not silently clear pending round state.

### Warmup / Round 1
- players spawn normally during warmup;
- race changes during warmup are reflected;
- no balance switch occurs during active warmup;
- first live prestart performs initial balance;
- players spawn at correct live T/CT spawn;
- no manual resurrection/spawn behavior fires.

### Normal balance
- balanced teams are left alone;
- >58/42 imbalance evaluates swaps;
- best candidate is selected;
- no move protection exists;
- four-round cadence works.

### Low population
- 1v2 through 1v5 scenarios can be selected when appropriate;
- nonlinear strength behaves as intended;
- bots remain filler.

### Disconnect
- 10v10 → 10v8 is corrected promptly;
- simultaneous disconnects coalesce;
- human candidate uses rating-aware simulation;
- follow-up strength check runs.

### Warcraft mechanics
- death then race respawn does not receive survival credit;
- temporary summon form does not replace base race assignment;
- multiple actual deaths remain represented;
- bot damage/kills do not affect player rating;
- custom summon/projectile attribution does not double count.

## 44. Final Production Model

```text
PLAYER CONNECTS
      |
      v
SQLite lookup by SteamID64
      |
      v
rating + latest real rounds in RAM
      |
      v
Warcraft base race/level attached
      |
      v
combat events update RAM only
      |
      v
ROUND ENDS
      |
      +--> snapshot real round
      +--> update historical/race models
      +--> one SQLite transaction
      |
      v
EVERY 4 ROUNDS
      |
      v
evaluate team strength
      |
      v
minimal live-match correction if needed

PLAYER DISCONNECTS
      |
      v
flush persistent state
      |
      v
evict player from RAM
```

The persistence layer is SQLite-only. The active game loop remains RAM-first,
bounded, indexed, and designed so historical player growth does not translate
into proportional gameplay resource usage.
